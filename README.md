# Digibank Go

A simplified digital bank API built in Go, exploring event-driven architecture with Apache Kafka. Built as a portfolio project to demonstrate REST API design, Kafka producer/consumer patterns, and PostgreSQL integration.

## Overview

This project simulates core digital banking operations — account creation, balance queries, and transfers between accounts — using an asynchronous, event-driven flow instead of synchronous request processing.

Instead of debiting/crediting balances directly inside the HTTP request, the API publishes a transfer event to Kafka and responds immediately. A separate consumer processes the event in the background, applying the same UX pattern used by real banking apps (e.g. a "processing..." screen that resolves a few seconds later).

## Architecture

The project follows a **handler → service → repository** layered pattern:

```
cmd/api/main.go          → application entrypoint, wiring dependencies
internal/handler/        → HTTP handlers (parse requests, call services/producers, write responses)
internal/service/        → business logic (balance validation, transfer rules)
internal/repository/     → database access (PostgreSQL queries)
internal/model/          → domain structs (Account, Transaction)
internal/kafka/          → Kafka producer and consumer
```

### Transfer flow

```
Client
  │
  ▼
POST /transfers ──► API validates request, creates a "pending" transfer record,
  │                 publishes a TransferMessage to the "transfers" Kafka topic
  ▼
202 Accepted (transfer_id returned immediately)
                              │
                              ▼
                    Kafka topic: "transfers"
                              │
                              ▼
                    Consumer (goroutine, consumer group "transfer-processor")
                              │
                    checks idempotency (processed_transfers table)
                              │
                    applies the transfer inside a SQL transaction
                    (debit + credit, BEGIN/COMMIT/ROLLBACK)
                              │
                    updates transfer status to "completed" or "failed"

Client polls: GET /transfers/{id}/status
```

## Why Kafka?

Processing the transfer synchronously (debit → credit → respond) would tie the API's response time to the database's write latency and make the whole request fail if any downstream step failed. Publishing an event instead:

- **Decouples** the API from the processing logic — the API only needs to know a transfer was requested, not how it gets processed.
- **Improves resilience** — if the consumer or database is temporarily unavailable, the event stays queued in Kafka instead of being lost.
- **Absorbs load spikes** — the API can accept requests faster than the database could process them synchronously.

The trade-off is that clients no longer get an immediate confirmation — they get a `202 Accepted` and must poll `GET /transfers/{id}/status` (or, in a real system, receive a push notification) to know when the transfer actually completed.

## Key technical decisions

- **Amounts stored in cents (`int64`)**, never floats — avoids floating-point rounding errors common in financial systems.
- **SQL transactions for transfers** — the debit and credit updates run inside a single `BEGIN`/`COMMIT`/`ROLLBACK` block, so a failure partway through never leaves the ledger inconsistent.
- **Idempotency via `transfer_id`** — Kafka guarantees *at-least-once* delivery, meaning the same message can be delivered more than once. Each transfer gets a UUID generated by the handler; before processing, the consumer checks a `processed_transfers` table and skips messages it has already handled. This was manually verified by republishing a duplicate message and confirming the balance was only updated once.
- **Consumer runs as a goroutine**, not a separate process — a deliberate simplicity trade-off for a portfolio project. In production, the consumer would typically run as an independently deployable/scalable service, decoupled from the API's lifecycle.
- **Consumer group (`transfer-processor`)** — if multiple consumer instances were added later, Kafka would automatically distribute messages between them without duplicate processing.
- **Repository functions take only the parameters they need** (e.g. `owner string, balance int64` instead of a full `Account` struct) rather than whatever's convenient to pass.

## Tech stack

- **Go** (`net/http` standard library, no framework)
- **PostgreSQL** — persistence
- **Apache Kafka** (+ Zookeeper) — event streaming, via `segmentio/kafka-go`
- **Docker / Docker Compose** — local infrastructure

## Running locally

### Prerequisites
- Go 1.22+
- Docker Desktop

### 1. Start infrastructure

```bash
# PostgreSQL
docker run --name digibank-postgres -e POSTGRES_PASSWORD=senha123 -e POSTGRES_DB=digibank -p 5432:5432 -d postgres

# Kafka + Zookeeper
docker compose up -d
```

### 2. Create the Kafka topic

```bash
docker exec -it digibank-go-kafka-1 kafka-topics --create --topic transfers --bootstrap-server localhost:9092 --partitions 1 --replication-factor 1
```

### 3. Create the database schema

```bash
docker exec -it digibank-postgres psql -U postgres -d digibank
```

```sql
CREATE TABLE accounts (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    owner VARCHAR(255) NOT NULL,
    balance BIGINT NOT NULL DEFAULT 0,
    created_at TIMESTAMP NOT NULL DEFAULT NOW()
);

CREATE TABLE transfers (
    id UUID PRIMARY KEY,
    from_account_id UUID NOT NULL,
    to_account_id UUID NOT NULL,
    amount BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'pending',
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMP NOT NULL DEFAULT NOW()
);

CREATE TABLE processed_transfers (
    transfer_id UUID PRIMARY KEY,
    processed_at TIMESTAMP NOT NULL DEFAULT NOW()
);
```

### 4. Run the application

```bash
go run cmd/api/main.go
```

The server starts on `:8080` and the Kafka consumer starts in the background automatically.

### 5. Run tests

```bash
go test ./... -v
```

## API Reference

A ready-to-use [Postman collection](./postman/digibank-api.postman_collection.json) is included, covering all endpoints below.

| Method | Endpoint                       | Description                          |
|--------|---------------------------------|---------------------------------------|
| POST   | `/accounts`                    | Create a new account                  |
| GET    | `/accounts/{id}`               | Get account by ID                     |
| GET    | `/accounts`                    | List all accounts                     |
| POST   | `/transfers`                   | Request a transfer between accounts   |
| GET    | `/transfers/{id}/status`       | Check transfer processing status      |

### Example: create an account

```bash
curl -X POST http://localhost:8080/accounts \
  -H "Content-Type: application/json" \
  -d '{"owner":"Jane Doe","balance":10000}'
```

### Example: request a transfer

```bash
curl -X POST http://localhost:8080/transfers \
  -H "Content-Type: application/json" \
  -d '{"from_account_id":"<uuid>","to_account_id":"<uuid>","amount":500}'
```

Response:

```json
{"status":"processando","transfer_id":"<uuid>"}
```

### Example: check transfer status

```bash
curl http://localhost:8080/transfers/<transfer_id>/status
```

```json
{"transfer_id":"<uuid>","status":"completed"}
```

## Known limitations & possible next steps

- The consumer commits Kafka offsets automatically after reading a message, even if processing fails afterward — a production system would typically use manual offset commits to guarantee reprocessing on failure.
- The consumer runs as a goroutine inside the same process as the API; a more resilient design would run it as a separate, independently scalable service.
- No authentication/authorization layer.
- No dead-letter queue for messages that repeatedly fail to process.
